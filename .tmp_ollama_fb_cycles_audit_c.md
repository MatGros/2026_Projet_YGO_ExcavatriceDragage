### 🔴 Écarts BLOCK (bloquants — sécurité ou contrat)

#### B1. Machine d'état : transition `RUN → HOLD` sans condition de sécurité
- **Fichier** : `CODE/G_CYCLE.st:142`
- **Règle** : `AF_Partie-04 §3.2` — toute sortie de `RUN` vers un état non-sûr doit être conditionnée par un défaut ou une commande explicite.
- **Constat** : La transition `RUN → HOLD` est déclenchée par `b_HoldCmd` (IHM) **sans vérification** que le mouvement en cours est dans une phase sûre (ex. `b_MoveActive`). Un opérateur peut figer le cycle en pleine course, laissant un actionneur sous tension.
- **Impact** : Risque physique (mouvement bloqué sans arrêt d'urgence).
- **Recommandation** : Conditionner par `NOT b_MoveActive` ou forcer un `SafeStop` interne avant `HOLD`.

#### B2. Défaut latched : `Reset` non testé sur front montant
- **Fichier** : `CODE/G_CYCLE.st:210`
- **Règle** : `AF_Partie-03 §1bis` — `Reset` doit être traité sur front montant (`F_Trig`), jamais en niveau.
- **Constat** : `IF b_Reset THEN` (niveau). Si l'IHM maintient `b_Reset` à `TRUE`, le FB se réinitialise en boucle dès qu'un défaut apparaît, masquant le défaut réel.
- **Impact** : Défaut intermittent non visible, cycle repart sans diagnostic.
- **Recommandation** : Utiliser un `R_TRIG` sur `b_Reset`.

### 🟠 Écarts MAJOR (fonctionnels ou testabilité)

#### M1. Homing : séquence non protégée contre les fins de course
- **Fichier** : `CODE/G_CYCLE.st:88-95`
- **Règle** : `AF_Partie-04 §5.1` — homing doit vérifier les capteurs de fin de course avant tout mouvement.
- **Constat** : La séquence `HOMING` démarre le mouvement sans vérifier `b_LimitMin`/`b_LimitMax`. Si la machine est déjà en butée, le mouvement force contre la butée.
- **Impact** : Usure mécanique, risque de casse.
- **Recommandation** : Ajouter une condition `IF NOT b_LimitMin AND NOT b_LimitMax THEN` avant le départ.

#### M2. Nombres magiques : temporisation de cycle en dur
- **Fichier** : `CODE/G_CYCLE.st:175`
- **Règle** : `CODE_QUALITY_STANDARDS.md §4.2` — aucune constante en dur dans le code applicatif.
- **Constat** : `TON_Cycle.PT := T#5S;` (5 secondes en dur). Non paramétrable, non testable en simulation rapide.
- **Impact** : Testabilité réduite, maintenance difficile.
- **Recommandation** : Exposer `r_CycleTime` en entrée ou en constante nommée `C_CYCLE_TIME`.

#### M3. Interface IHM : commandes non verrouillées (boutons poussoirs vs bascules)
- **Fichier** : `CODE/G_CYCLE.st:45-50`
- **Règle** : `AF_Partie-03 §2.3` — les commandes IHM doivent être des impulsions (`b_StartCmd`, `b_StopCmd`) et non des niveaux.
- **Constat** : `b_Start` et `b_Stop` sont des niveaux. Si l'IHM reste sur `TRUE`, le FB redémarre immédiatement après un arrêt.
- **Impact** : Comportement imprévisible, non conforme aux standards machine.
- **Recommandation** : Renommer en `b_StartCmd`/`b_StopCmd` et traiter sur front.

#### M4. Variables mortes : `i_StepCounter` jamais lu
- **Fichier** : `CODE/G_CYCLE.st:12`
- **Règle** : `CODE_QUALITY_STANDARDS.md §5.1` — aucune variable déclarée sans usage.
- **Constat** : `i_StepCounter` est incrémenté mais jamais utilisé dans la logique ni exposé en sortie.
- **Impact** : Confusion, code mort, testabilité faussée (on croit qu'il y a un suivi d'étape).
- **Recommandation** : Supprimer ou exposer en sortie `i_StepOut`.

#### M5. Câblage observable : accès direct aux internes du FB
- **Fichier** : `CODE/MAIN/PRG_MAIN.st:78`
- **Règle** : `CODE_QUALITY_STANDARDS.md §3.3` — encapsulation stricte, pas d'accès aux variables internes depuis l'extérieur.
- **Constat** : `G_CYCLE_1.i_StepCounter := 5;` (écriture directe dans l'instance depuis le PRG). Casse l'encapsulation, rend l'état non déterministe.
- **Impact** : Impossible de garantir la machine d'état, testabilité nulle.
- **Recommandation** : Passer par une méthode `SetStep()` ou supprimer l'accès.

### 🟡 Écarts MINOR (style, conventions, robustesse)

#### m1. Nommage : `b_` préfixe pour les booléens IHM
- **Fichier** : `CODE/G_CYCLE.st:45`
- **Règle** : `NAMING_CONVENTION.md §2.1` — les entrées IHM doivent être préfixées `x_` (booléens) ou `b_` réservé aux internes.
- **Constat** : `b_Start` est une entrée IHM mais préfixée `b_` (interne).
- **Impact** : Confusion lecture/maintenance.
- **Recommandation** : Renommer en `x_StartCmd`.

#### m2. Régions/commentaires : commentaire obsolète sur `HOLD`
- **Fichier** : `CODE/G_CYCLE.st:140`
- **Règle** : `CODE_QUALITY_STANDARDS.md §6.1` — les commentaires doivent refléter l'implémentation.
- **Constat** : `// HOLD = arrêt immédiat` mais le code ne fait pas d'arrêt immédiat (il attend la fin du pas).
- **Impact** : Mauvaise interprétation par un mainteneur.
- **Recommandation** : Corriger le commentaire ou la logique.

#### m3. DUT : enum `E_G_CYCLE_STATE` non typé en `UINT`
- **Fichier** : `CODE/G_CYCLE_ENUM.st:1`
- **Règle** : `AF_Partie-03 §4.1` — les enums doivent être typés explicitement (`UINT`, `INT`) pour la portabilité.
- **Constat** : `TYPE E_G_CYCLE_STATE : (IDLE, RUN, HOLD, HOMING, FAULT); END_TYPE` (type implicite).
- **Impact** : Dépend de la plateforme, risque de débordement.
- **Recommandation** : Ajouter `: UINT` après le nom.

#### m4. Testabilité : pas de sortie de diagnostic `diagCode`
- **Fichier** : `CODE/G_CYCLE.st:20`
- **Règle** : `AF_Partie-03 §5.2` — tout FB doit exposer un `diagCode` (WORD) pour le diagnostic.
- **Constat** : Absence de `diagCode` en sortie.
- **Impact** : Impossible de tracer les défauts en runtime.
- **Recommandation** : Ajouter `diagCode : WORD` et le renseigner à chaque transition.
